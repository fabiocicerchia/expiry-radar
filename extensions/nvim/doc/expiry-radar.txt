1. INTRODUCTION                                     *expiry-radar-introduction*

expiry-radar inventories everything that expires across an estate — TLS
certificates, the intermediate CAs nobody tracks, secrets, IAM keys, Vault
leases, domains — and ranks it by blast radius, so the certificate on the
payment path outranks the one on a staging dashboard.

This plugin runs that CLI and puts its answers where you already look: the
quickfix list, diagnostics on the config file, a float, and one string for
your statusline.

Two things it deliberately does NOT do:

- It never collects on a keystroke, and never on every save. A collection
  dials real hosts, queries RDAP and calls cloud APIs; registries rate-limit
  RDAP, and expiry dates move on the scale of days. See
  |expiry-radar-config-trigger|.
- It never quietly drops a source that failed. A run that lost an account
  produces an inventory that reads exactly like a clean estate, which is the
  failure this tool exists to prevent — so a lost source is on the float, in
  the statusline, and in a notification.

==============================================================================
2. REQUIREMENTS                                     *expiry-radar-requirements*

- Neovim 0.11 or newer (`vim.system`, `vim.fs.root`, `vim.validate`).
- The `expiry-radar` binary: >
    go install github.com/fabiocicerchia/expiry-radar/cmd/expiry-radar@latest
<
  Or `make build` in a checkout, which writes `./bin/expiry-radar`.

The plugin finds the binary on its own: `./bin/expiry-radar` in the project,
then `expiry-radar` on `$PATH`, then `$GOBIN`, `$GOPATH/bin` and `~/go/bin`.
Point `cmd` at it when it lives somewhere else.

==============================================================================
3. SETUP                                                   *expiry-radar-setup*

`setup()` is optional — a command used before it runs gets the defaults. Call
it to change them: >lua

    require('expiry-radar').setup({
      collect = { trigger = 'interval', interval_minutes = 120 },
      diagnostics = { warn_within_days = 21 },
    })
<
With lazy.nvim: >lua

    {
      'fabiocicerchia/expiry-radar',
      -- The plugin is a subdirectory of the CLI's repository.
      config = function()
        require('expiry-radar').setup({})
      end,
      cmd = { 'ExpiryRadar', 'ExpiryRadarReport', 'ExpiryRadarList' },
    }
<
Sources are opt-in: nothing runs implicitly. Point the plugin at an
`expiry-radar.json` (`:ExpiryRadarConfig` creates one), or set `endpoints` and
`domains` in `setup()` for a config-free project.

4. COMMANDS                                             *expiry-radar-commands*

                                                                *:ExpiryRadar*
:ExpiryRadar            Collect now. Preempts a running automatic collection.

                                                          *:ExpiryRadarReport*
:ExpiryRadarReport      The inventory in a float: failed sources first, then
                        every item grouped by deadline, ranked by blast
                        radius. `q` or `<Esc>` closes it.

                                                            *:ExpiryRadarList*
:ExpiryRadarList        Every item in the quickfix list. Items declared in the
                        config file jump to the line that declared them;
                        everything else carries its facts as text, because a
                        certificate discovered on an Ingress has nowhere in
                        this repository to jump to.

                                                          *:ExpiryRadarFilter*
:ExpiryRadarFilter      Pick one deadline window or one kind; its items go to
                        the quickfix list.

                                                           *:ExpiryRadarHover*
:ExpiryRadarHover       What the inventory already knows about the host or
                        domain under the cursor — including the intermediate
                        CAs its chain depends on. Says explicitly when a
                        source failed, because "clean" and "never checked" are
                        not the same answer.

                                                           *:ExpiryRadarProbe*
:ExpiryRadarProbe [host]
                        Probe one host right now, ignoring the config: its
                        certificate, its chain and its registration. Without
                        an argument it uses the host under the cursor, and
                        prompts if there isn't one.

                                                          *:ExpiryRadarExport*
:ExpiryRadarExport [format] [path]
                        Render a report to a file. Formats: `html`, `ical`,
                        `json`, `prometheus`. Prompts when given nothing.
                        The iCal feed is renewals as calendar events, with the
                        alarm lead time set by blast radius.

                                                             *:ExpiryRadarAdd*
:ExpiryRadarAdd         Record something. Most of the inventory is discovered —
                        you grant read access and the sources enumerate — but
                        three things are recorded: an endpoint to probe, a
                        domain to look up, and a `manual` item for what nothing
                        can discover at all (a registrar with no RDAP, a
                        credential rotated by hand, a code-signing certificate
                        on somebody's laptop).

                        Prompts for the kind first, seeds the value from the
                        host under the cursor, and validates the date against
                        the same rule the CLI applies — so it cannot write a
                        config the CLI then refuses to load. Appends as text, so
                        your indentation and key order survive, opens the file
                        at the new line, and collects straight away.

                        For a manual item the kind is not cosmetic: it picks the
                        base blast radius, which decides where the item lands in
                        the ranking.

                                                          *:ExpiryRadarRemove*
:ExpiryRadarRemove      Stop tracking a recorded item. Lists what the config
                        recorded and removes the one you pick.

                        Only recorded items are offered. A discovered one has
                        no entry to delete — removing a line would not remove a
                        certificate from an Ingress — and offering it would
                        imply this tool writes to your estate, which it never
                        does. To change an entry rather than remove it, use
                        |:ExpiryRadarList| and jump to its line.

                        Refuses outright if the config has changed since the
                        collection that reported the position: better to ask for
                        a refresh than to delete the wrong entry.

                                                          *:ExpiryRadarConfig*
:ExpiryRadarConfig      Open the config file, creating it from
                        `expiry-radar.example.json` if there isn't one.

                                                          *:ExpiryRadarCancel*
:ExpiryRadarCancel      Cancel the running collection.

                                                             *:ExpiryRadarLog*
:ExpiryRadarLog         What ran, what it took, and every source that failed.

5. CONFIGURATION                                   *expiry-radar-configuration*

Defaults: >lua

    require('expiry-radar').setup({
      enabled = true,
      cmd = {},              -- empty auto-detects; see |expiry-radar-requirements|
      config_path = '',      -- empty uses <root>/expiry-radar.json
      endpoints = {},        -- extra hosts, on top of the config file
      domains = {},          -- extra domains, on top of the config file
      extra_args = {},       -- appended to every invocation, verbatim

      collect = {
        trigger = 'on_config_save_and_interval',
        debounce_ms = 1500,
        interval_minutes = 60,
        on_startup = true,
        timeout_ms = 120000,
        within_days = 0,     -- 0 is everything, which is the point
        min_priority = 0,
      },

      diagnostics = {
        enabled = true,
        warn_within_days = 14,
        info_within_days = 30,
      },

      status = { warn_within_days = 14 },
    })
<
                                                 *expiry-radar-config-trigger*
`collect.trigger` is one of:

  `on_config_save`               collect when the config file is saved
  `on_config_save_and_interval`  that, plus a periodic refresh (default)
  `interval`                     only refresh periodically
  `manual`                       only when a command asks

Only the config file triggers a collection on save. Every other save in a
repository has nothing to do with what the estate has expiring.

`collect.within_days` and `collect.min_priority` are passed to the CLI, not
applied to the list afterwards, so an export contains exactly what the list
shows rather than a wider set.

==============================================================================
6. DIAGNOSTICS                                       *expiry-radar-diagnostics*

Items declared in the config file are published as diagnostics on the line
that declared them: the `host` in `endpoints`, the string in `domains`.

Everything else — a certificate on an Ingress, a key in IAM, a lease in Vault
— gets none. Nothing in the repository declared it, so there is no honest line
to attach it to; those live in the list and the float.

Severity follows the deadline, never the ranking:

  expired                          ERROR
  within `warn_within_days`          WARN
  within `info_within_days`          INFO
  beyond that                      nothing published

A certificate on the payment path ninety days out is the top of the list and
still nothing to interrupt an edit over.

==============================================================================
7. STATUSLINE                                         *expiry-radar-statusline*

`require('expiry-radar').statusline()` returns one string: the soonest
deadline, marked, with `(incomplete)` appended when the last run lost a
source. The soonest deadline rather than the highest priority — one string in
the corner is a clock.

lualine: >lua

    sections = { lualine_x = { require('expiry-radar').statusline } }
<

==============================================================================
9. HEALTH                                                 *expiry-radar-health*

`:checkhealth expiry-radar` answers the question a collection cannot: why it
produced nothing at all. It checks the binary, the config file, and — for
every source the config enables — whether the credentials that source needs
are actually in the environment Neovim was launched from. Credentials never
come from the config file, so an enabled source with an empty environment is
the most common way to get a clean-looking report missing an entire account.

10. RECORDING ITEMS                                    *expiry-radar-recording*

The sources split in two.

*Discovered* — you grant read access and the source enumerates: `k8s`, `vault`,
`aws`, and the chain intermediates behind every endpoint. You never list these,
which is the point: the ones that bite are the ones nobody remembered to list.

*Recorded* — you name it and a source reads its deadline: `endpoints` (dialled
over TLS) and `domains` (looked up over RDAP).

Between them sits everything that expires that no system will tell you about.
That is what `manual` is for: >json

    {
      "manual": [
        { "name": "acme-corp.co.uk", "kind": "domain", "expires": "2027-03-01",
          "labels": { "public": "true" } },
        { "name": "code-signing", "kind": "tls_cert", "expires": "2026-11-15",
          "namespace": "release" }
      ]
    }
<
`expires` takes YYYY-MM-DD or a full RFC 3339 timestamp; a bare day means its
start in UTC, which errs towards warning early. `kind` is one of `tls_cert`,
`intermediate_ca`, `secret`, `iam_access_key`, `vault_lease`, `domain`, and it
picks the base blast radius rather than being a label — a misspelt one is
rejected at load rather than ranked on a middling default.

Otherwise a manual item is treated exactly like a discovered one: `namespace`
and `labels` feed the same evidence, and `overrides` match it by name. Nothing
sits at the bottom of the report for having been typed in.

|:ExpiryRadarAdd| writes these for you.
